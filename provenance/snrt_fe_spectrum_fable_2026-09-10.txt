**Verdict first: the plan is not approvable as written.** The mode it specifies cannot start in the current tree, and its retained Fe restriction makes the mode unusable with any stellar or AGN source. Both are decisions the plan must make explicitly, not implementation details. Note that implementation is already in flight: `dust_iron_optics.f90` gained the generated Fe node include between two of my reads, the spectral contract already parses the new mode name, the header already carries a six-bin branch, and the HDF5 writer already binds both node hashes. I reviewed the plan against that live state.

## Q-GOAL and Q-LEAN

**Q-GOAL: yes, with one condition.** Group 8 in the medium table explicitly lists Fe spectral extension as incomplete, and the primary band is where electric-only Fe optics are most defensible: spin absorption matters in the far-IR, not above 0.01 eV. The connection replaces a grey four-bin operator that ignores Fe columns entirely. The condition is that the result must be runnable with a real source. Under the plan as written it is not (finding 2).

**Q-LEAN: the scope is already close to minimal.** The in-flight code confirms it: one bin-count field on the grain struct, one bounded C entry with a bin argument, one generated include, one new kind. Do not add a separate Fe-only operator or a second smoke program. Keep the denser-quadrature measurement, since the Fe L edges near 710 eV and the K edge near 7.1 keV sit inside groups 8 and 9 and nothing in `dust_fe_band128_manifest.json` records it yet. Keep the single MPI2/OMP2 live/restart run, since it is the only thing that exercises the field layout and restart identity.

## Blocking findings

1. **The mode is unsatisfiable in the current tree.** Fe carriers exist only with CHIMES on: the validator at `dust_mass_physics.f90:395` requires CHIMES, the layout at `read_hydro_params.f90:696` places Fe after the 157 species and errors otherwise, and CHIMES itself needs the CHIMES build. Every spectral mode error-stops in a CHIMES build at `snrt_spectral_contract.f90:117`, and the in-flight admission at `snrt_ramses_driver.f90:334` now requires Fe enabled while rejecting CHIMES. So "use the existing Fe mode", "keep CHIMES rejected" and "no namelist meaning change" cannot all hold. The right resolution is to admit the static Fe comparison without CHIMES: place the two Fe fields after the dust window when CHIMES is off, relax the validator for the static case only, require condensation zero and kinetics off in that case since both reconcile through CHIMES, and update the generator NVAR profile. The plan must say this, because it changes the prerequisites of an operator-approved namelist selection.

2. **The retained 4 eV rule plus maxent reconstruction rejects every Fe cell that sees any photon in groups 2 to 9.** The header at `snrt_band_spectrum.h:140` returns failure when Fe is present and any node above 4 eV has positive packet weight. Maxent weights are positive at all nodes, so a group-2 packet with a 2.4 eV mean still populates nodes up to 5.6 eV and aborts. That is stricter than the grey rule it replaces, which allowed group 2. Only group-1 photons below 1 eV survive, and no source in the repo emits only there. The live test in the evidence section therefore cannot contain Fe absorption above 1 eV, and the six-column Fe branch would be exercised live only by sub-eV photons or not at all. The plan must choose: keep the cap and declare the mode a group-1 comparison whose live run verifies wiring only, or replace the cap in this mode with the same declared no-photoelectron-escape limitation the D03 mode already carries. I recommend the second, since the missing escape energy is the same kind and size of error already accepted for graphite and silicate above their thresholds. That loosens an approved bound, so it needs the operator's word, not a silent edit.

## Optional refinements

- **Zero-Fe equivalence can be asserted bitwise.** With zero Fe columns the six-bin loop adds exact zeros and the iron flag is false, so demand identity, not a tolerance.
- **The Fe rejection reuses return code 9**, which the secondary-table failure also uses, so the driver prints a generic transport failure instead of the Fe message. Give it its own code.
- **The Fe builder duplicates the D03 node and declaration code.** Importing it is cleaner but not worth churn now that it exists.
- **Far-IR Fe emission remains electric-only** and underestimates cooling. Shared temperature with C and silicate mutes this. It is already declared, so no action beyond keeping the declaration.
